# Threat model

## Scope

Текущая модель охватывает офлайн MVP 0.1.0. Оператор запускает проверенный код на собственном устройстве или учебной VM. Облачные меры ниже являются требованиями к будущему сервису, а не выполненными гарантиями.

Активы: конфигурация и scope, целостность кода, синтетические события, findings, audit log и среда оператора. Возможные источники угроз: ошибочная конфигурация, недоверенный ввод, вредоносное изменение модуля, подмена отчёта и будущий недоверенный пользователь сервиса.

## Границы доверия

Конфигурация недоверенная и проверяется до запуска. Код встроенных модулей доверенный: Python-интерфейсы не являются sandbox. `lab://` — логическая метка, не сетевой адрес. Отчёт после записи на диск контролируется владельцем файла, поэтому не является доказательством неизменности аудита.

| Угроза | Текущий контроль | Остаточный риск |
| --- | --- | --- |
| Ошибочный scope | `authorized` строго true, точное совпадение allowlist | Реальность разрешения не проверяется |
| Сетевое воздействие | Встроенный сценарий только генерирует события | Изменённый Python-код может обходить ограничения |
| Инъекция | Фиксированный реестр, неизвестные поля отклоняются | ОС не ограничивает код проекта |
| Недопустимая телеметрия | Проверки synthetic, цели, последовательности, kind/outcome | Нет универсальной схемы внешних источников |
| Большая конфигурация | CLI 64 KiB, до 100 целей, фиксированное число событий | Библиотечный API не ограничивает размер JSON-файла |
| Подмена результатов | Детерминированный отчёт и тесты | Нет подписи или неизменяемого хранения |
| Утечка информации | Только синтетические данные | Сообщения об ошибках могут содержать локальный путь |
| Зависимости и supply chain | Только стандартная библиотека | Python и git всё равно должны быть доверенными |

## Безопасные границы

Разрешены синтетические учебные сценарии, проверка правил, анализ ошибок конфигурации и демонстрации в собственной лаборатории. Не включайте реальные credentials, production-данные, exploit payloads, произвольные команды, внешние адреса или инструкции для несанкционированного доступа. Согласование scope происходит до запуска и не выводится из наличия технического доступа.

Для публичных issues используйте вымышленные идентификаторы и минимальные примеры. Перед публикацией отчёта проверьте пути, имена лабораторий и данные окружения. Уязвимости сообщайте по [SECURITY.md](SECURITY.md).

## Требования к будущему облаку

- Аутентификация, RBAC и tenant isolation на каждом API и объекте хранения.
- Непривилегированные workers с ограничениями CPU, памяти, времени и egress.
- Подтверждённый scope, проверка при создании и выполнении задания, запрет production по умолчанию.
- Централизованный аудит отказов и запусков, защита от изменения, ограниченный доступ и retention.
- Защита секретов вне репозитория, очистка временных данных, тесты остановки и изоляции.

Перед каждым новым типом интеграции пересматривайте активы, границы, каналы утечки и негативные тесты. Более ранний краткий документ [docs/THREAT_MODEL.md](docs/THREAT_MODEL.md) сохранён для совместимости; актуальная расширенная модель находится здесь.
