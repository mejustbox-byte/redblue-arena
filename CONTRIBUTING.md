# Contributing

## Рабочий процесс

1. Обсудите существенную архитектурную доработку в issue без секретов или чувствительных логов.
2. Проверьте `git status`, ветку и актуальный upstream; сохраните чужие изменения.
3. Прочитайте применимые `AGENTS.md` и обязательные правила. `CLAUDE.md` не требуется для обычной работы, если обязательное правило не предписывает его чтение.
4. Создайте отдельную ветку и внесите ограниченное изменение.
5. Выполните тесты и обновите затронутую документацию и CHANGELOG.
6. Откройте PR с проблемой, новым поведением, проверками и ограничениями.

## Проверки

```bash
python3 -m unittest discover -s tests -v
python3 -m redblue_arena --config examples/lab.json
git diff --check
```

Тесты должны проверять наблюдаемое поведение: корректный finding, отсутствие finding ниже порога, раздельный подсчёт целей, отказ без авторизации и отказ вне allowlist. Для новых сценариев нужны безопасные fixtures и негативные проверки. Не используйте реальные системы, сеть, секреты или персональные данные в тестах.

## Требования к изменениям

Поддерживайте Python 3.12.x, стандартную библиотеку и фиксированный реестр до отдельного решения об изменении архитектуры. Не расширяйте сетевые возможности незаметно: предложите модель угроз и изоляции. Сохраняйте существующие файлы и лицензионные уведомления; избегайте не относящихся к задаче массовых правок.

Документируйте параметры, ошибки, schema_version, ограничения правил и статус функций. README описывает доступные возможности, INSTALL — проверенные команды, ROADMAP — планы, CHANGELOG — реальные изменения. LICENSE остаётся MIT; изменения правового текста требуют отдельного обсуждения.

## Публичный OPSEC

Примеры используют только `lab://` и вымышленные события. Перед PR проверьте diff на секреты, внутренние адреса, локальные пути, идентификаторы клиентов и содержимое отчётов. Уязвимости не публикуйте в обычном issue: следуйте SECURITY.md. Проект не принимает реальные эксплойты или инструкции для несанкционированных атак.

## Проверки платформы 0.2.0

Модули/API и миграция описаны в MODULE-API.md, HTTP endpoints — в API.md. Для control plane обязательны тесты tenant isolation, RBAC denial, scope, quotas, cancel/timeout, restart, audit tamper detection, retention и HTTP Host/Origin. REDBLUE_DOCKER_TESTS=1 включает реальные проверки контейнера после build. Никогда не подменяйте skipped Docker tests утверждением об успешной изоляции.

Изменение JSON schema требует явного schema_version и migration note. Не обещайте public cloud readiness по результатам local HTTP tests. Dev data, tokens и databases должны оставаться вне git.
